# Build Crawler

외부에서 데이터를 가져오는 기능을 만들거나 고칠 때(위임자의 위임 프롬프트 작성, 대행자의 구현, 검증자의 판정) 아래 규칙을 따른다.

## 0. 대상별 프리셋

- 공모전 수집은 `presets/contest.md`가 담당한다. 필터 낱말·제외 조건·제목 정리 규칙·정렬은 그 파일이 원본이고, 이 파일의 일반 규칙과 다르면 프리셋이 우선한다.
- 새 수집 대상에 반복되는 기준이 생기면 `presets/<대상>.md`로 추가한다.

## 1. 같은 대상·다른 수집처는 같은 필터 조건

- 수집하는 대상이 같고 수집하는 장소(사이트·API·페이지)만 다르면 필터 조건을 동일하게 한다. 포함·제외 낱말, 기간·마감 조건, 정렬, 수집 범위(페이지 수·건수)를 수집처마다 따로 정하지 않는다.
- 조건은 한 곳(n8n은 규칙 Code 노드 하나, 코드는 상수 모듈 하나)에만 정의하고, 수집처별 노드·함수는 그 값만 참조한다. 수집처별 리터럴 조건이 0개인지 검사하는 테스트를 둔다.
- 수집처가 조건을 지원하지 않으면(예: 서버가 정렬 파라미터를 무시) 그 수집처만 넓게 받아 오고, 같은 공통 필터로 거른다. 예외 사유는 그 노드 notes·코드 주석에 남긴다.
- 수집처를 추가할 때도 기존 공통 조건을 그대로 쓴다.

## 2. 별도 언급이 없으면 최신 기록부터

- 사용자가 정렬·범위를 따로 말하지 않았으면 가장 최신 기록(최근 등록·갱신순)을 가져온다. 사이트 기본 정렬이 최신순이 아니면 최신순 파라미터를 명시한다.
- "최신"의 뜻은 대상 타입이 정한다. 공모전(contest)은 마감이 얼마 남지 않은 것(마감 임박순)이고, 타입별 정의는 `presets/<대상>.md`에 둔다.
- 사용자가 정렬 기준(예: 마감일순)을 정했으면 그 기준을 모든 수집처에 같게 적용한다(1절).
- 수집 범위 밖으로 밀려 빠지는 항목이 없게, 범위 끝 항목의 날짜가 기간 조건을 넘는지 확인한다.

## 3. 수집 필터링과 라벨링·정리는 별도 단계

- 단계를 나눈다: ① 수집(파싱만, 거르지 않음) → ② 수집 필터링(공통 조건으로 포함·제외 판정) → ③ 라벨링·정리(제목 줄이기, 분류, 형식 변환, 중복 표시) → ④ 저장.
- 라벨링·정리 단계의 낱말 목록(예: 제목에서 지울 낱말)을 필터링·중복 판정 조건으로 재사용하지 않는다. 필터링과 중복 판정은 정리 전 원래 값으로 한다.
- 정리 단계는 항목을 버리지 않는다. 버리는 판단은 ② 필터링에서만 하고 사유를 남긴다.
- 저장소에 정리된 값만 남기면 다음 수집의 중복 판정이 틀어지므로 원래 값(제목·원본 링크)을 함께 저장하거나 원본 링크로 대조한다.

## 4. 검증

- 유닛 테스트는 바꾼 노드·함수마다 대표 사례만 둔다. 검증자는 유닛 테스트를 다시 돌리지 않는다.
- 검증은 실제 실행으로 한다: 원본 수 = 기록 + 제외 + 삭제(`[verify-step] loss-check …`)와 수집처마다 사이트가 직접 내준 목록 대 저장소 API 대조(`[verify-step] site-coverage …`). 규칙 원본은 `~/ai/skills/role-verifier/references/flow.md`다.
- 목표에 특정 항목을 쓸 때는 그 항목이 지금도 유효한지(마감·삭제) 원본에서 먼저 확인한다.
