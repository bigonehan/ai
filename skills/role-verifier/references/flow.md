# 흐름 검증 (기본 모드)

새 기능 구현 뒤와 오류 수정 뒤 모두 이 절차다. 흐름의 모든 행을 대행자가 제출하고 위임자가 배포한 뒤 한 번 실행한다.

- 위임자가 배포한 산출물로 시작한다. 이번 시작 동작·최종 효과에 참여한 실행 주체의 버전이 배포 버전과 같은지 먼저 한 번 대조한다. 화면이 참여하지 않는 서비스 흐름은 UI를 열지 않는다.
- 행마다 사용자 입력(텍스트 입력, 버튼 클릭, 명령 실행 등 실제 시작 동작)을 그대로 수행하고, 화면·반환값·파일·소비자 결과가 요구 결과와 같은지 본다. 런타임별 실행 기록 줄은 `runtime-<종류>.md`를 따른다.
- 순서는 `mock 사례:`(있을 때만, 경계·횟수 확인) → `실제 흐름:`(필수)이다. mock 사례가 통과해도 끝내지 않고, 배포본에서 실제 데이터·실제 외부 연동(n8n·Grist·Bridge 등)으로 시작 동작부터 최종 소비자까지 진행한 결과로만 `통과`를 보고한다. 위임 프롬프트가 mock만 지시해도 실제 흐름을 생략하지 않으며(`dispatch-agent`가 `실제 흐름:` 줄 없는 검증자 프롬프트를 거부), 실제 흐름이 사용자 데이터를 지우는 동작이면 실행 전 사본을 만들고 실행 뒤 되돌린다. readback은 실제 흐름에서 읽은 값만 쓴다. 실제 흐름 하니스에서는 제품 함수(Grist 갱신·로거·Webhook 등)를 스텁·대체하지 않고 로그도 제품이 쓰는 실제 경로에서 읽는다. 바꿀 수 있는 것은 사용자 데이터 보호용 입력 사본(Vault·폴더 경로)뿐이다. 실제 흐름을 마치면 `[verify-step] real-flow <실제 시작 동작 → 실제 외부 연동 → 최종 소비자 값>` 한 줄을 출력한다. 이 줄이 없거나 readback에 mock·가짜 표기가 있으면 `task-complete`가 통과를 거부한다.
- 제품 명령(초기화·생성 버튼 등)이 만드는 파일·문서는 미리 Vault·템플릿을 탐색하지 않고 명령을 실행해 생긴 경로를 확인한다.
- 화면 표시(`🔳`)와 사용자 흐름 판정은 검증자 몫이다. 대행자의 `rule_schema` 판정 타입은 다시 확인하지 않는다.
- 결과를 행마다 `grist task-hidden <id> --project <dir> --purpose "<사용자 입력 → 요구 결과 라벨>" --test "<재실행 가능한 확인 명령>"`으로 기록한다. `--test`는 `flow-wait`이 위임자 환경에서 다시 실행하므로, 호출자 역할에 따라 결과가 달라지는 사례(권한 거부 등)는 `env T26_ROLE=… T26_ROW=… T26_ROWS=…`를 명령에 명시한다.
- 마지막 보고 앞에 행마다 `readback: <행> <런타임> <필드>=<실제 값> … version=<실행 주체 버전>` 한 줄을 출력한다(예: `readback: 603 blender scene=1 frame=0-120 addon=0.0.10`). 이 줄이 없는 verify 로그는 Stop hook이 성공 보고 근거로 인정하지 않는다.
