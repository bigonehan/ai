# 3단계: 검증·전체 흐름·완료 (`manage-project` — Verify & Complete)

행이 `$H=검증`에 도달하면 `task-submit`의 `submit.changed`를 확인한다. 1~2개 파일 행은 숨긴 사례(`task-hidden`)와 `flow-wait`를 생략하고 최신 `task-confirm`을 흐름 증거로 사용한다. 0개·3개 이상·수치 없음은 일반 경로를 따른다. 버전·빌드·배포가 필요한 제품 변경과 최종 소비 결과 확인은 파일 수와 관계없이 수행한다. 이 단계에서 메인이 처음 맡는 행은 이미 받은 `row` 줄이 없을 때만 `grist task <id>`로 한 번 읽는다. 이미 확인 단계까지 진행한 작업에 사용자가 완료를 확인하면 기존 대화에서 확정한 행 ID와 `.ai/changes` 경로를 그대로 사용하며 자동 `$H=완료` 전환은 하지 않는다. 경로·명령·소스를 `read-architecture`·`rg`·도움말로 다시 찾지 않는다.

> 테스트를 새로 작성·실행할 때는 `verify-work`, 종료 판정이 막히면 `Complete_task`의 해당 절만 `rg -n`으로 발췌한다. 같은 작업에서 이미 읽은 Skill은 다시 읽지 않는다.

## 1. 숨긴 사례 검증 (`Flow 5: Hidden cases`, main)

- 각 행이 `$H=검증`이 되면 에이전트가 보지 못한 새로운 입력·경계값·빈 값 사례로 `task-hidden`을 실행한다:
  ```bash
  ~/ai/scripts/bin/grist task-hidden <id> --project <dir> --purpose "<원하는 결과 라벨>" --test "<새 입력 테스트 명령>"
  ```
- 통과하면 `.ai/changes`의 `### 구현` 아래에 다음 형식으로 기록된다:
  ```markdown
  #### 확인 (#<id>)
  - 목적 : <원하는 결과 라벨>
  - 결과 : 성공|실패
  - 상세 : <함수명(message/body) ▷ 반환값 또는 실패 위치 한 줄>
  ```
- 실패하면 해당 행 에이전트에 수리 경계 1회로 재배정한다.

## 2. 버전·빌드·배포 및 전체 흐름 테스트 (`Flow 6: Flow test`, main)

1. **단일 릴리스 및 배포 복사**
   - 현재 흐름의 모든 행이 `$H=검증`이 된 뒤 전체 흐름 테스트 전에 메인이 한 번만 수행한다:
     - 제품 동작이 바뀐 경우 patch 버전을 `0.0.1` 올리고(`package.json`, `manifest.json`, `public/manifest.json`, `runtime-contract.js`, `Cargo.toml` 등 일치), 빌드 산출물(`dist/manifest.json` 등) 버전을 확인한다.
     - 실행 가능한 산출물을 `/mnt/h/code/<프로젝트 디렉터리명>`(Obsidian 플러그인은 `.obsidian/plugins/<프로젝트명>`)에 복사한다.
     - 새 확장 빌드를 공용 CDP 브라우저(`127.0.0.1:9222`, `/home/tree/.config/codex-run-cdp`)에 로드할 때는 `fish -c 'run_cdp --replace -e /mnt/h/code/<프로젝트명> --detach'`를 사용한다.
2. **최종 소비 결과 확인 (`verify-work`; CDP가 필요한 경우에만 `run-cdp` + `access-stagehand`)**
   - 오류 보고와 개발 모드 로그가 있으면 먼저 해당 요청 ID의 실패 경계를 읽는다. 수정 뒤 `focused/unit → production-boundary integration → built artifact`에서 필요한 경계를 검증하고, 최종 소비 결과를 저장 상태나 상관 로그로 읽는다. 보이는 조작 자체가 바뀌었거나 로그·저장 상태로 최종 효과를 판정할 수 없을 때만 CDP 전체 흐름을 실행한다. 이미 작동하는 진단 로거의 출력 형식만 바꾸는 항목은 해당 형식 함수와 기존 로거 호출을 단위 테스트로 확인한다. 사용자가 검증 범위를 더 좁게 명시하면 그 범위와 미검증 경계를 기록한다.
   - 사용자가 원인과 해로운 동작을 이미 지정했다면 이를 `진단` 입력으로 사용해 소유 경계를 먼저 고친다. 창·로그·설치본을 열어 같은 사실을 다시 입증하지 않는다. 수정 후 전체 흐름에서 버전이 있는 런타임은 설치 산출물과 **이번 요청의 시작 동작·최종 효과에 실제 참여한 실행 주체**의 버전을 한 번 대조한다. UI 변경이나 UI 조작이 이번 흐름에 포함될 때만 화면 버전을 읽는다. 파일 감시·가져오기·삭제 같은 서비스 흐름에 화면이 참여하지 않으면 UI를 열지 않는다. 이전 실행의 로그나 빌드 파일 값만으로 실행 버전을 대신하지 않는다. 참여 주체의 버전이 불일치하면 전체 흐름 검증 실패로 판정하고 `flow-wait`를 실행하지 않는다. 버전이 없는 런타임에는 이 비교를 요구하지 않는다.
   - Mock, 소스 문자열 검사, 빌드 성공, 단순 ACK, 빈 페이지는 사용자-visible 기능의 완료 증거가 아니다.
3. **5분 병목 감지 로깅 및 자동 깨우기 타이머 (`verify-work` 필수 절차)**
   - Stagehand/CDP 검증 실행 시 `STAGEHAND_STEP_LOG=1`을 켜서 `[stagehand-step]`(`cdp-attach`, `stagehand-create`, `page-resolve`, `session-ready`, `session-close`) 및 `[stagehand-bottleneck]` 중간 과정 로그가 남게 한다.
   - 검증·런타임 명령이 백그라운드 태스크(`task-*`)로 전환되면 **반드시 같은 턴에서 턴을 끝내기 전에 `schedule(DurationSeconds=300, TimerCondition="<task-id>")` 5분 깨우기 타이머를 설정**한다.
   - 5분 타이머가 울리거나 검증·API 탐색·반복 재시도가 누적되어 지연되면 타임아웃으로 덮지 말고 즉시 중간 로그를 읽어 병목 경계(핸들 미해제, 파이프 대기, 무한 폴링, Stagehand attach/API 호출 오류 등)를 찾고 소스 또는 `stagehand.mjs`를 수정한 뒤 `.ai/docs/performance.md`, `### 메모`, 그리고 Stagehand 관련인 경우 `~/ai/skills/access-stagehand/references/attach-notes.md`에 반드시 기록한다.
4. **흐름 결과 기록 및 `flow-wait` (`.ai/changes` 직접 읽기·편집 금지)**
   - 기록된 단계 내용을 다시 볼 때는 `~/ai/scripts/bin/grist task-show <id> --project <dir> --section 검증|확인`으로 그 블록만 읽는다.
   - 전체 흐름 확인 후 `.ai/changes` 파일을 직접 읽거나 편집하지 말고 아래 `task-confirm` 한 번으로 `- [○] <check>`, `- [●] 사용자 검토 대기`, `#### 확인 (#<id>)`를 함께 기록한다(`task-step`은 `○`·`●`를 거부한다):
     ```bash
     ~/ai/scripts/bin/grist task-confirm <id> --project <dir> --summary "[표시 기호] <입력 또는 이전 단계> ⇒ <구현 결과>" --check "<목적: 원하는 결과 라벨>" --detail "<실행한 함수 ⇒ 전달 대상 ▷ 반환값 한 줄 요약>" --evidence /dev/stdin <<'E'
     1. <목표 1줄에 대한 실제 관측 근거>
     2. <목표 2줄에 대한 실제 관측 근거>
     E
     ```
   - `--evidence`는 `grist goal <id>`의 목표 줄마다 한 줄(`N. <근거>`)이며 수가 다르면 거부된다. J1은 테스트 출력이 아니라 이 근거와 흐름 확인으로 판정하므로, 각 줄에 그 목표의 대상·동작·관측값(함수·파일·화면·반환값)을 적는다.
   - 근거에는 이 행에서 실제로 실행한 명령·숨긴 사례·화면에서 본 값만 쓴다. 예상값, 다른 행의 결과, 실행하지 않은 경우의 추정은 쓰지 않는다. 한 줄에 관측값 하나를 쓰고, 단위 테스트로만 확인한 값은 `(단위 테스트)`라고 밝힌다.
   - J1은 근거 문장이 목표를 덮는지만 판정하고 근거가 참인지는 확인하지 않는다. J1 통과는 숨긴 사례(`task-hidden`, 일반 경로)·전체 흐름 확인을 대신하지 않으며, `enforce`에서도 경로가 요구하는 이 단계들을 생략하지 않는다.
   - 이어서 다음 명령을 실행한다:
     ```bash
     ~/ai/scripts/bin/grist flow-wait --project <dir>
     ```
   - `flow-wait`는 제출·숨긴 테스트를 재실행하고 흐름 기록을 검사하며 `$H=검증`을 유지한다. 행별 `- 요약 :`의 표시 기호와 구현 경로를 번호 없이 `$D` 최신 한 줄로 기록한다. 작업 중 `$D`의 번호 목록 이력은 changes에 남긴다. 이후 `Complete_task`가 Jev와 완료 목록 판정을 통과시켜 `$H=확인`으로 전환한다.
   - 사용자 전용 동작(로그인·인증, 결제·비용, 비가역 외부 전송, 브라우저 밖 OS 앱 조작)이 남은 경우에만 구체적인 단일 동작을 안내한다. 자동 단계는 `확인`까지만 기록한다.
   - 브라우저 클릭·확장 재로드·Settings `Test`는 사용자에게 넘기지 않고 직접 한다.

## 3. 완료 판정 및 응답 종료 (`Complete_task`)

1. **턴 종료 전 판정**
   - `~/ai/skills/Complete_task/SKILL.md`에 따라 테스트 출력과 목표, 완료 목록, 응답 종료 여부를 확인한다. 메인 세션은 현재 작업의 모든 행이 `# 완료`에 있고 `$H=확인` 또는 사용자가 설정한 `완료`일 때 종료할 수 있다.
   - 메인 세션만 최종 응답·질문·사용자 동작 요청 직전에 `fish -c 'nf -m "<작업명> <결과·요청 요약>"'`를 한 번 실행한다. 명령이 끝날 때까지 기다려 exit code를 확인하고, 명령을 재호출하지 않는다. 하위 에이전트와 hook에는 보내지 않는다.
2. **작업 목록 기록 (`task-complete` → `$H=확인`)**
   - 전체 흐름의 실제 결과가 준비되면 `Complete_task`가 목표와 결과를 대조하고, 기존 `### 구현` 내역에서 실제 작업만 추려 `#### 완료 (#<id>)` 번호 목록을 생성한 뒤 `# 완료`로 옮긴다. 형식은 다음과 같다:
     ```markdown
     #### 완료 (#<id>)
     1. [🏗️] <새로운 구조 변경 한줄 요약>
     2. [✨] <작업에 필요한 Flow, 논리, 컴포넌트, 새 기능 한줄 요약>
     3. [🌍] <외부 API, DB, 인증, 연결 한줄 요약>
     4. [⭕️] <누락된 결과 파일·변수·값의 수정 한 줄 요약>
     5. [🚀] <기존 구조의 속도 또는 흐름 개선 한줄 요약>
     ```
   - 예시의 모든 줄을 채우지는 않는다. 실제 완료한 유형만 기록하며, 오류 수정이면 `SKILL.md` 3절 `### 원인`의 오류 기호 10개(`🅰️ 🗝 ❌ ⭕️ 🔢 🛣 👥 🏷 🚥 🔳`) 중 원인에 맞는 기호를 쓴다.
   - 그 뒤 `~/ai/scripts/bin/task-complete --row <id> --project <dir>`를 실행한다. 통과하면 `$H=확인`과 목록 이동을 확인한다. 사용자의 "완료" 답변이 와도 이 명령을 다시 실행해 `$H=완료`로 바꾸지 않는다. 최종 `$H=완료`는 사용자가 직접 수정한다.
