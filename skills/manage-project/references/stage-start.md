# 초안·진단 단계 (`manage-project` — Start)

초안: 소유 프로젝트와 기존 행을 `initial-task`에서 판정한 뒤 요청을 기록하고 세부 사항마다 목표·행을 만든다.
초안: 위임 판단은 `references/plan.md` §2로 넘긴다.
진단: 관측 실패를 `$I`, 사용자 제공 또는 재현으로 찾은 원인을 `$J`에 기록한다.
진단: 원인(`$J`)이 없으면 **재현 위임**(대행자 재현 모드: 목표는 실패 재현과 `$J` 기록뿐, `task-red` 후 수정 없이 종료)을 먼저 하고, `$J`가 있으면 그 원인 경계를 목표로 **구현 위임**(`stage-work.md`)을 한다.

## 요청 기록 → 행 분리 → 목표 구체화 → 배정 (`Flow 0~3`)

- **정정·지적·오분류:** 소유 판정, 절차 지적 처리, 오분류 원복, 지정된 원인의 진단 연결은 `initial-task/SKILL.md` §3이 단일 원본이다.
- **범위·의도 파악:**
  - 사용자가 명시한 시작 동작(예: `초기화` 등)·구조·값·최종 효과만 범위다. 위임 전에 해당 시작 동작 함수와 연결된 기존 파일·템플릿 경로가 실제 대상 경로와 일치하는지 그 함수 범위만 먼저 확인해 프롬프트에 포함하며, 이를 확인하지 않은 채 위임한 뒤 뒤늦게 재위임하지 않는다. 이름이 나오지 않은 인접 workflow, Bridge, 공유 helper는 바꾸지 않는다.
  - 요구 1개는 `시작 동작 → producer → transport/handler → authoritative consumer → 최종 효과` 경로 하나로 검증해 완료 조건 한 줄과 맞추고, 요구에 없는 검증·증거를 더하지 않는다.
  - 증거용 Python·validator·recorder·contract 파일을 새로 만들지 않는다.
  - 이미 정해진 사실(사용자 메시지·`grist request` 출력·코드·규칙)은 다시 묻지 않고, 해석이 둘 이상이라 결과 workflow가 달라질 때만 수정 전에 묻는다.

0. **요청 기록 (`request-record`, main)**
   - `# 요구 사항`·`# 세부 사항` 두 절의 입력을 표준 입력으로 `request-record`에 전달해 오늘자 changes `# 요청` 절에 기록한다. `# 요구 사항`에는 채팅 원문을 복사하지 않고 사용자 요청을 한 줄로 요약한다. `# 세부 사항`에는 분리한 작업 단위마다 `[📐|✒️|⌨️|🚿|✏️|🌍] 한 줄 요약`을 쓴다. `📐`는 스키마·함수 타입 일치와 변환, `✒️`는 문서·템플릿 새 형식, `⌨️`는 설정 옵션, `🚿`는 필터, `✏️`는 계산식, `🌍`는 API·DB 연동이다. 요청 기록을 위해 `test/tmp/`나 다른 경로에 입력 사본을 만들지 않는다:
     ```bash
     ~/ai/scripts/bin/grist request-record --project <dir> --input-file /dev/stdin --title "<10자 미만 제목>" --summary "<요청 한 줄>" <<'INPUT'
     # 요구 사항
     - <사용자 요청의 한 줄 요약>

     # 세부 사항
     - [✒️] <문서·템플릿 새 형식 작업 단위 한 줄 요약>
     INPUT
     ```
   - 오늘자 `.ai/changes` 파일(`구현/업무/261008.작업관리기/형식/작업관리기.형식-changes.md` 형식)이 준비되고 `# 요청` 절에 블록이 추가되며 Obsidian 개발 문서 `# 📆`가 갱신된다. changes 파일명에 쓰는 날짜별 제목에는 현재 프로젝트·소스명을 넣지 않는다.
   - 사용자가 `[표시 기호] 한줄 요약`처럼 정확한 입력 형식을 제시했다면 그 형식과 입력을 만드는 지점을 첫 작업 단위에 보존한다. 독립된 인접 요청은 별도 작업 단위로 기록하고, 첫 형식의 실제 출력 확인을 인접 작업의 검사나 문서 정리로 대신하지 않는다.

1. **작업 행 분리 (`task-add`, main)**
   - `# 세부 사항` 한 줄이 Grist에 작성할 작업 단위 하나다(같은 파일을 건드리는 요구는 한 행에 묶는다). 기호를 포함한 그 한 줄을 Table26 `$B` 항목명과 changes `# 작업`·`## [구현]` 제목에 동일하게 전달한다. `# 요구 사항`의 문장을 Table26 행으로 대체하지 않는다.
   - 요구마다 `$H=초안`으로 Table26 행과 changes 블록(`# 작업`의 `N. <세부 사항과 동일한 기호·문구> (#<id>)` 및 `# 진행`의 `## [구현] <세부 사항과 동일한 기호·문구> (#<id>)`)을 만든다(`- 판정 :` 줄은 `[값]` 또는 `[상태]`를 골라 `--judge "[값|상태] <한줄 판정 내용>"`으로 작성한다):
     ```bash
     ~/ai/scripts/bin/grist task-add --project <dir> --type "기능 추가|개선|오류 해결" --judge "[값|상태] <한줄 판정 내용>" --fields '{"A": <Table7 ID>, "B": "[✒️] <# 요청 세부 사항 한 줄 요약>", "H": "초안"}' --goal-file /dev/stdin --summary '<목표 한 줄 요약>' <<'GOAL'
     1. [기능] <목표 한 줄>
     GOAL
     ```
   - 목표는 행을 만들 때 함께 기록한다(아래 2번 규칙). J3가 목표를 막으면 행이 만들어지지 않으므로 목표를 고쳐 같은 명령을 다시 실행한다. 출력의 `row` 줄이 새 행 조회이며 별도 `grist task <id>`를 실행하지 않는다.

2. **목표 작성 규칙 (`task-add --goal-file`, 정정은 `task-goal`)**
   - 목표는 `inquire-task` Skill로 세부 사항 한 줄을 측정 단위(한 줄 = 관측값 하나)로 분해해 쓴다.
   - 각 행의 상세 목표를 `[연결|기능|수정]` 태그와 `▷`(리턴값) / `⇒`(전달 대상) 기호를 쓴 한 줄 요약들로 작성한다(JSON 원문 객체나 `변형:` 줄은 쓰지 않고 `message`/`body` 또는 핵심 값만 적는다).
   - 사용자가 명시한 요구만 넣으며, 해석이 둘 이상이라 결과 workflow가 달라질 때만 수정 전에 묻는다.
   - 새 행의 목표는 1번 `task-add --goal-file`로 기록한다. `$H=초안`인 행의 목표를 정정할 때만 같은 인자로 `~/ai/scripts/bin/grist task-goal <id> --project <dir> --goal-file /dev/stdin --summary '<한 줄>'`을 실행한다. 목표 전달에 임시 파일을 만들지 않는다.
   - 목표 읽기는 `~/ai/scripts/bin/grist goal <id> --project <dir>`로만 한다. changes 파일을 열어 목표를 찾지 않는다.

3. **에이전트 배정 (`Assign`, main — 프로젝트당 1개)**
   - 전역 규칙·Skill 절차 텍스트 행의 마감 예외는 `manage-global-rules` §4와 `stage-verify.md`를 따른다.
   - 서브에이전트는 띄울 때마다 `read-architecture`·행 조회·Skill 읽기·소스 탐색을 처음부터 반복하므로 토큰은 동시 실행 수가 아니라 호출 횟수로 늘어난다. 호출 횟수를 줄이는 기준으로 배정한다:
     - 위임 판정과 실행은 `references/plan.md` §2를 따른다.
   - 에이전트 프롬프트 내용은 `role-delegator`의 위임 프롬프트 계약을 따른다. 행 번호(`--row`)·`row:` 줄·목표는 `dispatch-agent`가 붙이므로 옮겨 적지 않는다.
   - 서브에이전트를 띄운 직후 호출자가 `cargo run --quiet --manifest-path ~/ai/skills/record-log/scripts/record-log/Cargo.toml -- start <project dir> <row> --role <codex_<row>|t26_<row>> --conversation <conversationId> --caller <own char> <own name>`(`record-log` Skill)을 실행해 에이전트 번호와 호출자를 행 메모에 기록한다(메인은 `0 main`). 출력된 11자 ID를 서브에이전트 메시지로 전달하고, 서브에이전트는 선택한 작업 게이트에 `--agent-id <ID>`를 전달해 기록 중복을 막는다. 서브에이전트 자신은 start를 실행하지 않는다.
   - 대행자 1명은 행 1개만 맡는다(역할 게이트가 `T26_ROW` 밖 행의 `task-submit`을 거부한다). 행마다 따로 `dispatch-agent --row <id>`로 위임한다.
   - 행이 외부 API(AI 사이트·Eagle·Grist·원격 서버 등)를 부르면 위임 프롬프트에 `record-log` Skill 형식 로그(`ID | 호출 함수 | 시도 | 결과`, 위 start로 받은 ID, `ack=`·`body.<필드>=`·`error=` 포함 120자 한 줄)를 각 호출 경계에 구현하고, 메인이 읽을 수 있는 로그 위치(프로젝트 `.ai/logs/YYMMDD.log` 또는 기존 개발 로그 파일)에 남기라는 요구를 넣는다. 구현자는 실패 시 그 로그 한 줄로 실패 경계를 찾을 수 있는지 테스트로 확인한다.
   - 메인이 이미 찾은 파일 경로·줄 범위를 프롬프트에 넣어 에이전트가 같은 탐색을 반복하지 않게 한다. `$J` 원인은 Grist에 기록하면 `row:` 줄로 전달된다.
   - 프로젝트가 여럿이면 수정 경로가 겹치지 않는 프로젝트 에이전트끼리만 최대 5개까지 병렬로 실행한다(한 번에 처리하는 에이전트는 5개로 제한).

### 진단 오류 기호 선택

원인 기호는 `~/ai/rules/rule_schema.md` 5절(오류 기호)을 따른다.
