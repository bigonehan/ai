# 2단계: 작업 및 구현 (`manage-project` — Work)

`t26_<id>` 서브에이전트가 코드를 작성·수정하거나, 단위 테스트를 돌리거나, 오류·회귀(`Failure loop`)를 진단·수리하거나, 이름을 변경(`Renames`)할 때 이 문서를 읽고 실행한다(수정 파일 1~2개 행은 메인이 직접 이 절차를 따르고, 3개 이상 묶음만 `t26_<id>`가 맡는다).
- UI·레이아웃 변경이 포함되면 `~/ai/skills/implement-ui/SKILL.md`를 함께 읽는다.
- 테스트 작성·실행 전에는 `~/ai/skills/verify-work/SKILL.md`의 경계 규칙을 확인한다.

## 1. 구현 절차 (`Flow 4: Agent procedure`)

1. **행·목표 확인 (전체 파일 읽기 금지)**
   - 메인이 프롬프트에 넣은 `row` 줄(`H=… | I=… | J=… | K=…`)로 행을 읽는다. `row` 줄을 받지 못했을 때만 `~/ai/scripts/bin/grist task <id>`를 한 번 실행한다.
   - `.ai/changes` 파일을 파일 읽기·편집 도구로 직접 열지 않는다. `~/ai/scripts/bin/grist goal <id> --project <dir>`로 목표 줄만 읽는다(메인이 프롬프트에 넣었으면 그 출력을 쓴다). 목표는 절대 직접 수정하지 않는다. `$J`가 이미 있으면 그 원인 경계를 작업 기준으로 삼고 별도 가설로 화면·로그·설치 상태를 탐색하지 않는다.
2. **소유 경계와 검증 대상 기록 (`[▷]`)**
   - 오류 수정은 아래 **Failure loop**로 `$I`와 `$J`를 기록하고 그 `task-update` 출력의 `row` 줄에 있는 `$J` 경계를 수정한다. 원인이 불명확하면 그 실패의 재현 테스트 작성·실행으로 원인을 먼저 찾는다. 설치·버전·실행 상태를 반복 조회해 이미 알려진 실패를 재진단하지 않는다.
   - 함수 초안을 만들거나 조정하고 `~/ai/scripts/bin/grist task-step <id> --project <dir> --step "▷" --text "<구현 내역>" --goal <목표 줄 N>`으로 기록한다(`.ai/changes` 직접 편집 금지).
   - 실제 입력으로 목표 줄들을 검증하고 목표 판정에 필요한 **핵심 필드·한 줄 결과값만** 발췌해 출력(`console.log(result.targetField)` 등)하는 단위 테스트를 작성한다(객체·요청 목록·문서 본문 전체를 덤프해 컨텍스트를 채우는 행위 금지).
   - 입력 형식 자체가 요구사항이면 그 입력을 생성하는 함수에 사용자가 준 예시를 넣어 기대 문자열과 비교한다. 저장·게이트·표시 단계의 검사만으로 입력 형식 구현을 통과시키지 않는다.
3. **원인에 맞는 작업 게이트 실행 (`$H=작업`)**
   - 원인 미확정: 사용자가 지적한 오류를 `$I`에 기록하고, 해당 실패를 `task-red`로 재현해 원인을 찾은 뒤 `$J`에 기록한다. `$J`를 기록한 `task-update`의 `row` 줄에 있는 원인 경계를 수정한다.
   ```bash
   ~/ai/scripts/bin/grist task-red <id> --project <dir> --purpose "<원하는 결과 라벨>" --test "<테스트 명령>" --tests <테스트 파일 경로> --paths <수정 허용 최상위 경로(쉼표 구분)>
   ```
   - 원인 확정: 사용자가 알려준 원인은 `$J`에 기록하고 그 출력의 `row` 줄을 쓴다(이미 `$J`에 기록되어 있으면 시작 조회를 사용한다). 실패 재현을 반복하지 않고 `task-ready`로 수정 범위와 수정 후 실행할 집중 테스트를 등록한다. 기존 로거의 출력 형식만 바꾸는 작업은 해당 포매터와 기존 호출의 단위 테스트를 지정한다.
   ```bash
   ~/ai/scripts/bin/grist task-ready <id> --project <dir> --purpose "<원하는 결과 라벨>" --test "<수정 후 테스트 명령>" --tests <테스트 파일 경로> --paths <수정 허용 최상위 경로(쉼표 구분)>
   ```
   - `task-red`는 assertion 실패가 조사 중인 원인과 연결되는지 확인한다. `task-ready`는 실패 여부를 검사하지 않는다.
   - 주의: `--paths`에는 `.` 대신 프로젝트 기준 최상위 경로 목록(예: `src,tests` 또는 `content.js,tests`)을 넣는다.
4. **본 구현 및 단위 테스트 (`[▶]`, `$H=교정`)**
   - 단위 테스트 중에는 `~/ai/scripts/bin/grist task-update <id> --project <dir> --fields '{"H": "교정"}'`으로 단계를 맞춘다.
   - 입력으로부터 결과를 계산하도록 구현하고, 목표 기대값을 리터럴로 하드코딩해 반환하지 않는다.
   - 문서·초기화·파서 로직에 분기(예: 신규 생성 분기와 `EEXIST` 기존 노트 읽기 분기)가 여러 개 있으면 모든 활성 분기에 새 정규화·형식을 누락 없이 적용한다.
   - 불필요한 해시·다이제스트 검증이나 해시 전용 로깅을 추가·유지하지 않고 실제 입출력 값과 consumer 상태로 검증한다.
   - `~/ai/scripts/bin/grist task-step <id> --project <dir> --step "▶" --text "<구현 및 단위 테스트 내역>" --goal <목표 줄 N>`으로 목표 줄(측정 단위)마다 기록한다(`.ai/changes` 직접 편집 금지).
   - 구현·테스트 중 오류나 실패 경계를 만나면 아래 **Failure loop**에 따라 `$H=진단`과 `$I`를 기록하고, 사용자 제공 원인 또는 재현으로 찾은 원인을 `$J`에 기록하고 그 출력의 `row` 줄을 쓴다.
5. **Submit 게이트 실행 (`task-submit` → `$H=검증`)**
   ```bash
   ~/ai/scripts/bin/grist task-submit <id> --project <dir>
   ```
   - `task-red` 또는 `task-ready`에 등록된 수정 후 테스트가 통과하고 허용 경로 밖 변경이 없으면 `#### 검증 (#<id>)`를 기록하고 `$H=검증`으로 바꾼다. 출력과 목표의 Jev J1 완료 판정은 `Complete_task`가 전체 흐름 뒤에 수행한다. 최종 소비 경로가 바뀐 기능은 해당 경로를 메인에게 전달한다. 출력 형식만 바뀐 기존 로거는 집중 단위 테스트 결과로 확인한다.
   - 실패 출력이 나오면 그 경계가 다음 수리 대상이다.
   - `t26_<id>` 서브에이전트는 자신의 행이 `검증`이 될 때까지 SubagentStop 훅에 의해 종료가 차단된다. 서브에이전트는 소스와 테스트만 수정하며 버전 올리기·빌드·배포 복사·사용자 질문·`확인`/`완료` 기록은 하지 않는다.

## 2. 오류·회귀 진단 루프 (`Failure loop`)

보고된 오류, 회귀, 동작하지 않는 기능, 테스트 실패는 모두 이 루프를 따른다.

1. **관찰 및 진단 기록 (`$I`, `$J`, `.ai/changes`)**
   - 사용자가 지적한 오류는 현재 작업의 Table26 `$I`에 최신 한 줄로 기록하고 이력은 `.ai/changes`의 `### 오류`에 보존한다. 사용자가 원인을 알려주면 그대로 `$J`에 기록한다. 원인을 알려주지 않았으면 지적된 실패를 재현해 원인을 찾은 다음 `$J`와 `### 원인`에 기록한다. `$J`를 쓴 `task-update`의 `row` 줄을 작업 기준으로 삼는다(별도 오류 행을 새로 만들거나 `$G`를 바꾸지 않는다; 작업 행이 없을 때만 새 행을 만들고 `AGENTS.md`에 연결한다).
2. **보고된 관측으로 실패 경계 확정**
   - 사용자가 제공한 실제 런타임 증거(콘솔 예외, 렌더링 화면, 실패 경로의 상태값, 명령 출력)와 결함 위치를 먼저 `$I`·`### 오류`에 기록한다. 알려준 원인은 `$J`에 기록하고, 원인이 없을 때만 같은 실패를 재현해 찾는다. `$J` 재조회 후 그 원인 경계를 수정한다. 이미 보고된 불일치를 수정 전 설치·버전·실행 여부 조회로 재진단하지 않는다.
3. **원인 분류 (`### 원인`, `$J`)**
   - `[오류 기호] 한줄 요약 : {리턴된 에러메시지 Body}` 형식으로 적는다. `$J`는 같은 `[오류 기호] 한 줄`이며 `task-update`가 기호 없는 줄을 거부한다.
   - 오류 기호 10개와 고르는 기준은 `SKILL.md` 3절 `### 원인` 한 곳을 따른다(`🅰️ 🗝 ❌ ⭕️ 🔢 🛣 👥 🏷 🚥 🔳`).
   - `$D`에는 `진단` 진입 때 `[오류 기호] <점검할 내용 한 줄>` 한 줄만 쓴다.
4. **단계 게이트**
   - `작업/교정 → 진단` 전환 시 같은 `task-update`에 `$I`와 `$D`(`[오류 기호] 점검 한 줄`)를 함께 기록한다(빠지면 거부된다). 사용자가 원인을 알려주거나 재현으로 찾은 뒤에는 같은 행의 `$J`를 기록하고 그 출력의 `row` 줄을 쓴다. 원인이 아직 특정되지 않았다면 `$I`에 확인된 오류를 남긴 채 그 실패의 재현을 이어간다:
     ```bash
     ~/ai/scripts/bin/grist task-update <id> --project <dir> --fields '{"H": "진단", "I": "1. <오류 요약>", "D": "[<오류 기호>] <점검할 내용 한 줄>"}'
     ```
   - 원인 확정 뒤에는 `task-update <id> --project <dir> --fields '{"J": "1. [<타입>] <원인 요약> : {<에러 Body>}"}'`로 기록하고 출력 `row` 줄의 원인만 작업 기준으로 삼는다.
   - 원인이 불명확해 재현으로 조사한 경우에는 같은 입력의 테스트가 수정 후 통과하는지 확인한다. 사용자가 원인과 결함 경계를 지정한 경우에는 수정 전 실패 실행을 요구하지 않고, 해당 경계의 수정 후 테스트 통과로 `task-submit`에 진입한다.
5. **무음 실패 금지 및 로그 보안**
   - 사용자 동작 경로의 모든 조기 반환(early return)과 비동기 예외는 로그나 알림을 남겨야 한다.
   - 로그에 토큰·인증 헤더·원문 개인 payload·개인 전체 경로를 남기지 않는다.

## 3. 이름 변경 (`Renames`)

- 이름 변경 규칙의 단일 소유 섹션이다.
- 사용자가 프로젝트명, 기능명, 함수명, 폴더, 경로, 문서 형식, Skill, 플러그인 이름을 바꾸라고 하면 `.ai/docs/architecture.md`에서 고른 소유 폴더(`src/`, `server/` 등)만 대상으로 `rg -n`을 실행해 한 번에 모든 곳을 바꾼다(`/home/tree/extensions` 루트 전체 스캔·`.ai/changes` 이력 탐색 금지):
  - 제품 소스(`src/`, `server/`) 내 하드코딩된 Vault·템플릿 경로 문자열, 형제 consumer 프로젝트, `manifest.json`·표시 이름, 배포 대상 폴더의 산출물(이전 이름 산출물은 삭제), Obsidian 문서, Table7 `C`·`Obsidian_Id`.
- 호환성을 위해 이전 이름·별칭(alias)·레거시 경로를 남겨 두지 않고, 재설치·호환성 경고를 출력하지 않는다.
- 변경 후 테스트를 실행해 실패하는 외부 참조가 있으면 이전 이름을 복원하는 대신 그 외부 참조를 새 이름으로 고친다(`.ai/changes`의 과거 이력 줄만 예외).
