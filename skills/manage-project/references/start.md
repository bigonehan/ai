# 1단계: 작업 시작 (`manage-project` — Start)

새 작업 요청을 받았거나, 진행 중인 요청의 정정을 받았거나, 프로젝트를 처음 열었거나, 새 Table26 작업 행·목표를 만들고 에이전트를 배정할 때 이 문서를 읽고 순서대로 실행한다. 기존 작업을 "완료"·"잘 된다"고 확인하는 답변은 새 요청이 아니다. 이 경우 시작 절차와 `read-architecture`·파일 검색을 반복하지 말고 이미 아는 행·기록 경로로 답하며 자동 `$H=완료` 전환은 하지 않는다(`Complete_task`). 새 작업의 첫 파일 탐색 전에 사용자 메시지의 **수정 대상**을 사례·증상과 분리해 소유 프로젝트를 정한다(프로젝트 문서·코드는 전체를 읽지 않고 필요한 섹션·줄·필드만 `rg -n` 또는 `grist task-show --section`으로 발췌한다).

## 1. 구조 파악 (`read-architecture`) 및 문서 확인

1. 사용자 메시지에서 지목한 수정 대상의 프로젝트를 먼저 정한다. Skill·설계/검증 절차·에이전트 판단/토큰 낭비 지적은 제품 이름이나 삭제 사례가 있어도 작업관리기 루트(`/home/tree/extensions`)가 소유한다. 제품 동작 자체가 수정 대상인 요청에서만 해당 제품을 소유자로 고른다. 그런 다음 파일 읽기·검색 전 첫 명령으로 `~/ai/scripts/bin/read-architecture --project <소유 프로젝트> --query "<요청 키워드>"`를 실행한다(다른 프로젝트로 옮기면 다시 실행). 현재 작업 폴더에서 자동 출력된 구조가 다른 프로젝트 것이면 그 출력으로 대상을 바꾸지 않는다.
   - 출력에서 작업 대상 폴더와 후보 파일을 고른 뒤 `rg -n "<패턴>" <파일>`로 위치를 찾고 필요한 범위만 읽는다(`ls -R`, `find`, `grep -r`, 전체 `cat` 금지).
   - `missing` 또는 빈 템플릿(exit 2)이면 실제 프로젝트 기준으로 `.ai/docs/architecture.md`(`# 도메인`은 `항목 : 설명`, `# 구조`는 루트·2단계 폴더, 파일명 제외)부터 작성한 뒤 다시 실행한다.
   - 작업 중 폴더가 추가·삭제·이동되거나 구조 차이가 작업 범위 안이면 같은 작업에서 `.ai/docs/architecture.md`를 함께 갱신한다.
2. 기존 Table26 행은 `read-architecture` 뒤 `~/ai/scripts/bin/grist task <id>`로 `$H`·`$I`·`$J`·`$K`를 한 번 읽는다(ID를 모르면 `grist gate --cwd <dir>`로 찾은 직후). 새로 만들거나 기록한 행은 `task-add`·`task-goal`·`task-update` 출력의 `row` 줄이 조회이며 다시 조회하지 않는다. 컨텍스트 낭비와 자동 압축(`CHECKPOINT`)을 막기 위해 `AGENTS.md`(시스템 프롬프트에 이미 로드됨), 프로젝트 Obsidian 개발 문서, `.ai/changes/YYMMDD.<제목>.md` 전체를 파일 읽기 도구로 읽지 않고, 필요한 섹션·줄·필드만 `rg -n` 또는 `~/ai/scripts/bin/grist task-show <id> --project <dir> --section <섹션>`으로 발췌해 읽고 출력한다.

## 2. 초기화 여부 확인 (`Initialization check`)

- `/home/tree/extensions` 하위 프로젝트의 제품 파일을 바꾸기 전에 가장 먼저 확인한다.
- 프로젝트 `AGENTS.md` 맨 위에 `# 상태`(`### grist` 아래 `ID : <n>`, `### obsidian` 아래 `문서 : <경로>`, `### 실행` 아래 `runtime : <요약>`) 헤더가 없거나 `~/ai/scripts/bin/grist project <n>`이 행을 반환하지 않으면 미초기화 프로젝트다.
- 미초기화 프로젝트는 먼저 사용자에게 프로젝트 타입(`업무`, `공방`, `게임`, `보조` 중 택1)을 물어 `manage-project` 초기화 절차(`~/ai/skills/manage-project/references/initialize.md`)를 실행해 Obsidian 폴더·문서(`구현/[타입]/YYMMDD.<이름>/<이름>.md`, `일지/<이름>-개발.md`, `노트/`, `[타입].md`), Table7 행, `AGENTS.md`(`작업관리기.형식-Agents.md.md` 형식), `.ai/docs/`·`.ai/changes/`를 만든 뒤, 현재 요청을 아래 절차로 기록하고 이어간다.
- `grist gate`는 변경 파일이 있는 미초기화 프로젝트를 `uninitialized`로 보고하며, Stop hook이 턴 종료를 차단한다.

## 3. 요청 기록 → 행 분리 → 목표 구체화 → 배정 (`Flow 0~3`)

- **정정 분류:** 먼저 사용자가 고치라고 지목한 대상을 판정한다. 에이전트가 왜 화면 확인·설치 탐색·무관한 작업에 토큰을 썼는지 묻거나 Skill·설계/검증 절차의 수정을 요구하면, 언급된 플러그인의 삭제·버전 문제는 **오분류를 설명하는 사례**이며 작업관리기 루트가 소유한다. 기존 행은 위 시작 조회로 `$I`·`$J`를 읽는다. 새 오류 지적은 `$I`에 기록하고, 사용자가 알려준 원인은 `$J`에 기록한다. 원인이 없으면 해당 실패를 재현해 찾은 뒤 `$J`에 기록한다. `$J`를 쓴 `task-update` 출력의 `row` 줄에 있는 원인 경계를 작업 기준으로 삼는다. 그 후 소유 프로젝트의 최신 요청(`~/ai/scripts/bin/grist request --project <dir>`)과 열린 Table26 목표를 대조한다. 제품 자체 동작을 바꾸라는 별도 명시 요구가 없으면 제품 행·에이전트·배포를 만들지 않는다.
- **오분류 교정:** 사례 제품에 이미 잘못 만든 행·소스·테스트·버전 변경이 있으면 그 변경만 원복하고 취소 이력을 남긴다. 이를 중단된 제품 작업으로 간주해 다시 시작하지 않는다. 실제 소유 프로젝트에서 절차 수정과 적용 검증을 마친다.
- **정정 실행:** 사용자가 지적한 미충족 목표를 원래 요청의 한 줄 요약에 반영하고 `# 세부 사항`을 실제 수정 단위로 바로잡는다. 기존 행의 목표·기록으로 처리할 수 있으면 새 행을 만들지 않는다. 별개의 Skill·설정 변경을 명시한 경우에만 그 변경을 행으로 분리한다. 관련 파일의 수정과 소비 경계 확인을 마친 다음 결과를 보고한다.
- **절차 자체에 대한 지적:** 사용자가 Skill·절차가 불필요한 확인·탐색을 유발한다고 지적하면 진행 중인 확인을 멈춘다. 낭비를 강제한 기존 문구를 제거·수정하고 활성 적용을 확인한다. 사용자 요청에 속한 작업만 재개하며, 사례를 제품 작업으로 오분류해 시작했다면 그 작업은 원복·취소한다. 설명 문장만 추가하고 강제 문구를 남겨두지 않는다.
- **실패 위치가 지정된 정정:** 사용자에게서 이미 받은 원인·실패 상태·불일치·결함 위치를 기존 행의 `진단` 근거로 연결하고 실제 수정 파일의 소유 경계부터 고친다. 수정 전에 같은 사실을 입증하려고 화면·로그·설치본·버전·실행 여부를 반복 조회하지 않는다. 수정 후 검증은 해당 결함의 직접 소비 결과로 제한한다.
- **범위·의도 파악:**
  - 사용자가 명시한 시작 동작·구조·값·최종 효과만 범위다. 이름이 나오지 않은 인접 workflow, Bridge, 공유 helper는 바꾸지 않는다.
  - 요구 1개는 `시작 동작 → producer → transport/handler → authoritative consumer → 최종 효과` 경로 하나로 검증해 완료 조건 한 줄과 맞추고, 요구에 없는 검증·증거를 더하지 않는다.
  - 증거용 Python·validator·recorder·contract 파일을 새로 만들지 않는다.
  - 이미 정해진 사실(사용자 메시지·`grist request` 출력·코드·규칙)은 다시 묻지 않고, 해석이 둘 이상이라 결과 workflow가 달라질 때만 수정 전에 묻는다.

0. **요청 기록 (`request-record`, main)**
   - `# 요구 사항`·`# 세부 사항` 두 절의 입력을 표준 입력으로 `request-record`에 전달해 오늘자 changes `# 요청` 절에 기록한다. `# 요구 사항`에는 채팅 원문을 복사하지 않고 사용자 요청을 한 줄로 요약한다. `# 세부 사항`에는 분리한 작업 단위마다 `[📐|✒️|⌨️|🚿|✏️|🌍] 한 줄 요약`을 쓴다. `📐`는 스키마·함수 타입 일치와 변환, `✒️`는 문서·템플릿 새 형식, `⌨️`는 설정 옵션, `🚿`는 필터, `✏️`는 계산식, `🌍`는 API·DB 연동이다. 요청 기록을 위해 `test/tmp/`나 다른 경로에 입력 사본을 만들지 않는다:
     ```bash
     ~/ai/scripts/bin/grist request-record --project <dir> --input-file /dev/stdin --title "<10자 미만 제목>" --summary "<요청 한 줄>" <<'INPUT'
     # 요구 사항
     - <사용자 요청의 한 줄 요약>

     # 세부 사항
     - [✒️] <문서·템플릿 새 형식 작업 단위 한 줄 요약>
     INPUT
     ```
   - 오늘자 `.ai/changes` 파일(`구현/업무/261008.작업관리기/형식/작업관리기.형식-changes.md` 형식)이 준비되고 `# 요청` 절에 블록이 추가되며 Obsidian 개발 문서 `# 📆`가 갱신된다. changes 파일명에 쓰는 날짜별 제목에는 현재 프로젝트·소스명을 넣지 않는다.
   - 사용자가 `[표시 기호] 한줄 요약`처럼 정확한 입력 형식을 제시했다면 그 형식과 입력을 만드는 지점을 첫 작업 단위에 보존한다. 독립된 인접 요청은 별도 작업 단위로 기록하고, 첫 형식의 실제 출력 확인을 인접 작업의 검사나 문서 정리로 대신하지 않는다.

1. **작업 행 분리 (`task-add`, main)**
   - `# 세부 사항` 한 줄이 Grist에 작성할 작업 단위 하나다(같은 파일을 건드리는 요구는 한 행에 묶는다). 기호를 포함한 그 한 줄을 Table26 `$B` 항목명과 changes `# 작업`·`## [구현]` 제목에 동일하게 전달한다. `# 요구 사항`의 문장을 Table26 행으로 대체하지 않는다.
   - 요구마다 `$H=초안`으로 Table26 행과 changes 블록(`# 작업`의 `N. <세부 사항과 동일한 기호·문구> (#<id>)` 및 `# 진행`의 `## [구현] <세부 사항과 동일한 기호·문구> (#<id>)`)을 만든다(`- 판정 :` 줄은 `[값]` 또는 `[상태]`를 골라 `--judge "[값|상태] <한줄 판정 내용>"`으로 작성한다):
     ```bash
     ~/ai/scripts/bin/grist task-add --project <dir> --type "기능 추가|개선|오류 해결" --judge "[값|상태] <한줄 판정 내용>" --fields '{"A": <Table7 ID>, "B": "[✒️] <# 요청 세부 사항 한 줄 요약>", "H": "초안"}' --goal-file /dev/stdin --summary '<목표 한 줄 요약>' <<'GOAL'
     1. [기능] <목표 한 줄>
     GOAL
     ```
   - 목표는 행을 만들 때 함께 기록한다(아래 2번 규칙). J3가 목표를 막으면 행이 만들어지지 않으므로 목표를 고쳐 같은 명령을 다시 실행한다. 출력의 `row` 줄이 새 행 조회이며 별도 `grist task <id>`를 실행하지 않는다.

2. **목표 작성 규칙 (`task-add --goal-file`, 정정은 `task-goal`)**
   - 목표는 `inquire-task` Skill로 세부 사항 한 줄을 측정 단위(한 줄 = 관측값 하나)로 분해해 쓴다.
   - 각 행의 상세 목표를 `[연결|기능|수정]` 태그와 `▷`(리턴값) / `⇒`(전달 대상) 기호를 쓴 한 줄 요약들로 작성한다(JSON 원문 객체나 `변형:` 줄은 쓰지 않고 `message`/`body` 또는 핵심 값만 적는다).
   - 사용자가 명시한 요구만 넣으며, 해석이 둘 이상이라 결과 workflow가 달라질 때만 수정 전에 묻는다.
   - 새 행의 목표는 1번 `task-add --goal-file`로 기록한다. `$H=초안`인 행의 목표를 정정할 때만 같은 인자로 `~/ai/scripts/bin/grist task-goal <id> --project <dir> --goal-file /dev/stdin --summary '<한 줄>'`을 실행한다. 목표 전달에 임시 파일을 만들지 않는다.
   - 목표 읽기는 `~/ai/scripts/bin/grist goal <id> --project <dir>`로만 한다. changes 파일을 열어 목표를 찾지 않는다.

3. **에이전트 배정 (`Assign`, main — 프로젝트당 1개)**
   - 전역 규칙 원문 또는 Skill 절차 텍스트(`SKILL.md`·`references/*.md`)만 바꾸는 행은 메인이 직접 처리한다. 전역 규칙은 `agent-rules` 원본·생성본·상태를 확인한다. 두 종류 모두 다른 하위 프로젝트 `AGENTS.md`의 명시적 지시가 새 기준과 충돌하는지만 검사한다. 충돌이 없으면 `task-confirm`으로 실제 결과를 기록하고 `task-complete --row <id> --project <dir>`가 목표와 확인 증거를 판정해 `$H=확인`으로 전환한다. 충돌이 있으면 해소한 뒤 전환한다. 이 경우 `t26_<id>` 배정과 `task-red`·`task-submit`을 하지 않는다. 제품 코드·CLI·hook·Skill 스크립트 변경은 아래 배정 절차를 따른다.
   - 서브에이전트는 띄울 때마다 `read-architecture`·행 조회·Skill 읽기·소스 탐색을 처음부터 반복하므로 토큰은 동시 실행 수가 아니라 호출 횟수로 늘어난다. 호출 횟수를 줄이는 기준으로 배정한다:
     - 수정 파일이 1~2개인 작은 행(여러 하위 프로젝트에 흩어진 작은 행 포함)은 메인이 `t26_<id>` 없이 직접 `task-ready` → 수정 → 집중 테스트 → `task-submit`한다.
     - 수정 파일 3개 이상인 묶음만 프로젝트(수정 경로 묶음)마다 `t26_<첫 행 id>` 서브에이전트 1개(대화 문맥을 넘기지 않는 새 에이전트)에 그 프로젝트의 행을 모두 맡겨 순서대로 처리하게 한다. 행마다 따로 띄우지 않는다.
   - 에이전트 프롬프트에는 다음만 전달한다:
     - 프로젝트 경로와 첫 명령 `~/ai/scripts/bin/read-architecture --project <dir> --query "<키워드>"` 실행 지시
     - `Table26 #<id>`와 메인이 받은 최신 `row` 줄(에이전트는 이 줄로 행을 읽고 다시 조회하지 않는다)
     - 수정 허용 경로 목록(형제 프로젝트, 전역 설정, Skill, 다른 행의 파일 수정 금지)
     - `~/ai/skills/manage-project/references/work.md`를 읽고 오류는 `$I`, 사용자 제공 원인 또는 `task-red` 재현으로 찾은 원인은 `$J`에 기록한 `task-update`의 `row` 줄 경계를 수정하라는 지시(원인 확정이면 `task-ready` → 집중 테스트 → `task-submit`)
   - 서브에이전트를 띄운 직후 호출자가 `agent-id start <project dir> <row> --role t26_<row> --conversation <conversationId> --caller <own char> <own name>`을 실행해 에이전트 번호와 호출자를 행 메모에 기록한다(메인은 `0 main`). 출력된 11자 ID를 서브에이전트 메시지로 전달하고, 서브에이전트는 선택한 작업 게이트에 `--agent-id <ID>`를 전달해 기록 중복을 막는다. 서브에이전트 자신은 start를 실행하지 않는다.
