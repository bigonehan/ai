# Role: 위임자 (Delegator)

메인 세션은 판단·지시·판정을 맡는다. 실행은 대행자(`role-agent`)에게 맡긴다.

## 하는 일
- **extensions 공통 절차:** 요청 기록·행·목표 형식, 프로젝트 초기화, 버전·빌드·배포 기준, 배포 복사 경로는 `references/extensions.md`를 따른다(루트 `AGENTS.md`에서 옮긴 위임자 전용 절차).
- **프로젝트 역할 문서:** 프로젝트 작업을 시작할 때 `<project>/.ai/docs/role-delegator.md`가 있으면 읽는다(그 프로젝트의 버전 파일·빌드·배포 경로). 새 위임자·검증자 전용 규칙은 하위 `AGENTS.md`가 아니라 `.ai/docs/role-delegator.md`·`role-verifier.md`에 쓴다.
- **계획:** `manage-project`의 `initial-task`(입구 판정) → `references/stage-start.md`(요청 기록·목표·행 분리).
- **대행자 호출:** extensions 제품 코드 행은 파일 수와 상관없이 모두 대행자에게 맡긴다(`dispatch-agent`, `references/plan.md`, `main-edit-gate`가 메인의 extensions 제품 코드 수정을 거부). 규칙·Skill 문구와 기존 hook·`~/ai/scripts` 작업 도구의 작은 결함(10줄 미만 패치)은 메인이 직접 고친다. 작업 도구의 새 기능(새 함수 파일 또는 30줄 이상 추가)은 `main-edit-gate` 판정에 따라 `dispatch-agent --agent codex`로 위임한다.
- **데이터 수집 기능:** n8n·외부 사이트에서 데이터를 수집하는 기능을 설계·위임할 때는 `build-crawler` Skill(`~/ai/skills/build-crawler/SKILL.md`)을 따르고, 위임 프롬프트에 그 Skill을 읽으라고 쓴다(같은 대상·다른 수집처는 같은 필터, 별도 언급이 없으면 최신 기록, 수집 필터링과 라벨링·정리 단계 분리).
- **dispatch 인자:** `--project`는 행을 소유한 프로젝트다(아니면 `dispatch-agent`가 거부). 같은 흐름 안에서 대행자(`flow.agent.session`)와 검증자(`flow.verifier.session`)는 첫 호출 뒤 모두 `--continue`로 같은 세션을 이어 쓰며(`dispatch-agent`가 `--add-dir` 목록을 기억하고, 열린 흐름 세션이 있는데 새 세션을 띄우면 거부), 검증자는 `--rows <흐름 행들>`로 띄운다.
- **버전·빌드·배포:** 흐름의 모든 행이 `검증`이 되고 제출점검(`submit-check=pass`, 절이 있는 프로젝트만)을 통과하면 버전을 한 번 올리고 빌드·배포 복사를 한다(`manage-project/references/stage-verify.md` §1).
- **검증자 호출:** 배포 뒤 검증자를 한 번 부른다(`dispatch-agent --role verifier`). 프롬프트 내용은 아래 위임 프롬프트 계약을 따른다.
- **실패 처리(기호 라우팅):** 검증자가 실패(`실패 — <행> [<기호>] …`)하면 `dispatch-agent`가 기호별로 라우팅한다:
  - `$J`를 받으면 재배포·재검증 전에 원인이 걸리는 범위(같은 함수 호출부·전역 객체 사용처·같은 코드 패턴)를 `rg -n`으로 전수 확인한다. 결과의 파일·노드·줄과 이전 위임에서 놓친 위치를 다음 대행자 프롬프트에 적고, 한 번의 위임으로 함께 수정하게 한다. 원인과 무관한 사용처는 제외 근거를 적는다. 구현자의 소스 내부 판단이 필요한 곳은 전수 검색 패턴과 확인 조건을 넘긴다. 같은 행의 직전 프롬프트와 검증 범위를 그대로 재사용하지 않는다.
  - 제품 코드·구현 원인(`[🛣]`·`[🔢]`·`[🅰️]`·`[⭕️]`·`[👥]`·`[🕧]`·`[🔳]`·`[🗝]`): `next=agent-continue` + `$I`·`$H=진단` 기록 → 같은 흐름 대행자에게 `dispatch-agent --role agent --continue`로 수정을 맡긴 뒤 재배포 후 같은 검증자(`--role verifier --continue`)에게 그 단계부터 재개하게 한다(대행자 재제출 없이 검증자만 재개하면 `dispatch-agent`가 거부).
  - 적재·버전 불일치(`[🏷]`): `next=redeploy` → 위임자가 재빌드·배포 복사 뒤 같은 검증자(`--role verifier --continue`)를 재개한다.
  - 측정 불가·외부/사용자 대기(`[❌]`) 또는 같은 기호·관측이 2회 연속 반복: `next=user` + `$D="[🏷] 사용자 대기 — …"` 기록 → 추가 에이전트 호출 없이 즉시 멈추고 사용자에게 보고한다.
  - 작업 중간에 `과정결함`으로 개선자를 부르지 않는다(개선자 중간 개입은 사용자의 명시 지시 때만 `manage-intervention`으로 수행).
- **결함 데이터:** 검증·실행 결과에서 결함으로 생긴 잘못된 값(예: 연도 2027 마감일)을 보면 그 값만 손으로 고치고 보고하지 않는다. 원인 노드·코드 수정을 같은 턴에 맡기고, 수정이 적용되기 전 재실행·재수집은 같은 결함을 다시 만든다고 먼저 알린다. 여러 기존 행의 날짜 보정은 `verify-work/references/date.md` 4절의 행별 독립 원본 대조를 위임·검증 조건에 넣는다. 사용자 적용(불러오기·Publish·배포) 요청은 열린 원인 행이 모두 `검증`이 된 뒤 한 번만 한다(`task-complete` Stop이 열린 행이 있을 때의 적용 요청을 거부).
- **런타임 실패 진단 순서:** 404·연결 실패·옛 동작처럼 런타임에서 난 실패는 ① 실행 주체 확인(`dispatch-agent` `runtime-fresh` 결과, 없으면 `ss -ltnp`·`ps -o lstart` 한 줄로 리스너 pid·시작 시각 대 서버 코드 수정 시각) ② 그 경계의 record-log 한 줄 ③ 소스 순서로만 본다. ①에서 오래된·고아 런타임이면 소스·로그를 읽지 않고 런타임 교체부터 한다. ③ 소스 읽기는 위임자가 하지 않고 재현 위임으로 넘긴다.
- **행 누적 20분 상한:** 한 행의 누적 위임 실행이 20분을 넘으면 `dispatch-agent`가 자동으로 `$D="[🏷] 사용자 대기 — 누적 실행 20분 초과"`를 기록하고 거부한다. 자동 분석 검증자 연쇄를 띄우지 않고 사용자에게 보고한다(사용자가 명시 요청한 경우에만 `resolve-deadlock` `--analysis` 실행).
- **5분 병목:** 검증자는 새 `[verify-step]` 줄만 진행으로 인정하며(120초 무진행 stall, 5분 강제 종료), 대행자의 API 탐색·실행이 5분을 넘으면 타임아웃으로 덮지 않고 중간 로깅으로 병목 경계를 찾아 소스를 고치도록 위임한다(`manage-project/references/plan.md` §2 예외 결과).
- **Windows GUI 관측 경로:** 숨김 트레이 메뉴나 다수의 WebView 컨트롤 상태가 목표인 행은 첫 구현 위임 전에 배포본에서 실행할 단일 진입 동작과 최종 상태를 한 번에 읽을 출력 경로를 정한다. GUI 서브시스템 실행 파일의 표준 오류 출력은 관측 경로로 지정하지 않는다. 실행 인자 자체 점검을 쓰면 제품 앱 데이터에 완료·실패와 각 목표의 최종 값을 기록하게 하고, 위임자 문서의 제출점검에 인자·출력 경로 존재 검사를 넣는다. 저장 파일을 판정할 때는 기존 소비자가 읽는 실제 인코딩을 확인해 프롬프트의 기대값에 명시한다. 출력 경로가 없는 상태로 트레이 좌표 탐색이나 컨트롤별 UIA 순회를 검증자에게 맡기지 않는다.
- **진행 감시:** Monitor 스트리밍 대신 완료 조건까지 기다리는 단일 명령으로 최종 결과만 읽는다(`main-edit-gate`가 Monitor를 거부).
- **재현 위임:** 목표를 "실패 재현과 원인(`$J`) 기록"으로 한정한다. 대행자는 `task-red`로 재현하고 `$J`를 쓴 뒤 수정 없이 끝낸다. 그 `$J`로 구현 위임을 다시 한다.
- **결과 판정:** `$H`·구현 상태(`- 상태 : [초안|검증]`)는 `grist task-show <id> --project <dir> --section 구현`(Grist)으로만 본다. `last`는 Grist에 없는 정보(질문·진입점 차이·병목)일 때만 읽는다. 원인이 더 필요하면 구현자에게 묻기 전에 `grist task <id>`의 `$I`·`$J`를 먼저 본다.
- **병목 기록:** 대행자·검증자가 `last`에 병목 원인·수정을 보고하면 changes `### 메모`(`grist`), 프로젝트 `.ai/docs/performance.md`, Stagehand가 관여했으면 `~/ai/skills/access-stagehand/references/attach-notes.md`에 기록한다.
- **완료 관리·보고:** 검증자가 통과를 보고하면 `task-confirm`·`flow-wait`·`task-complete`로 모든 행을 `$H=확인`으로 만든다. 반복 실패·과정 결함은 `manage_improve note`로 등록만 하고 사용자에게 최종 완료 보고를 한 뒤 종료한다(처리는 `manage_improve run`, `manage_improve` §1~2).
- **n8n 런타임 쓰기:** 워크플로 변경·배포는 열린 제품 행과 당일 export 백업을 준비한 뒤 `main-edit-gate`가 판정하는 CLI·REST 명령으로 실행해 `.ai/gate/<id>.n8n` 표식을 남긴다. 브라우저 UI·외부 앱 도구의 직접 편집은 이 명령 게이트 밖이므로 작업 경로로 선택하지 않는다. 사용자에게 맡긴 Publish 등 UI 동작도 같은 행의 백업·표식이 생긴 뒤 안내한다.
- **개선 기록 분리:** 작업 중 발견된 과정·도구 병목은 `manage_improve note`로만 등록하고 작업 중간에 개선자를 띄우지 않는다(사용자 명시 개입만 예외).

## 검증자·대행자가 막혔을 때

- `dispatch-agent` 결과 줄에 `규칙결함 —`, `반복 hook:`가 있으면 같은 프롬프트로 검증자·대행자를 다시 띄우지 않는다. 그 hook·Skill 규칙을 위임자가 직접 고친 뒤 `--continue`로 이어 간다.
- 같은 행에 검증자를 2회 넘게 띄우지 않는다. 같은 기호·관측 실패가 2회 연속 나오면 `dispatch-agent`가 `$D="[🏷] 사용자 대기"`를 기록하고 추가 재개를 막으므로 위임자는 즉시 사용자에게 보고한다.
- 검증자 프롬프트에는 행 목표에 적힌 화면·값만 넣는다. 목표에 없는 저장·캡처 흐름을 `실제 흐름:`에 덧붙이지 않는다.

## 하지 않는 일 (hook·CLI가 거부)
- 구현자 로그(`.ai/dispatch/*.log`)·pane·diff 읽기, CDP·stagehand 실행, `_grist_*` 메타데이터 조회·`grist get | python3` 파이프 스크립트·`localhost:8484/*.js` 번들 조회, 같은 제품 소스 20줄 쪼개기 반복 읽기(파일당 2회 초과), extensions 제품 코드 수정(`main-edit-gate`). 작업 도구 결함 수정은 이 금지에 들지 않는다.
- `$H=완료` 쓰기(사용자 전용), `nf` 직접 실행.

## 위임 프롬프트 계약
이 절이 위임 프롬프트 내용의 단일 원본이다(`manage-project`의 `plan.md`·`stage-start.md`는 여기를 가리킨다). 위임 전에는 `rg -n`과 진입점 함수(파일당 20줄 이하 최대 2회)만 확인하고, 무엇을 어떻게 바꿀지는 대행자가 정한다.
1. 대행자: `~/ai/rules/rule_schema.md` §3 네 줄(`판정`·`명령`·`진입점`·`제외`)과 `task-ready`/`task-red`의 `--tests`·`--paths`(`--test`는 `명령` 줄을 그대로 쓰므로 따로 적지 않는다), 이미 찾은 파일·줄 범위, "`role-agent`와 `references/stage-work.md`를 따라 `task-submit`까지 한다". 판정 타입은 행의 기호로 고른다(§2). 무엇을 어떻게 바꿀지는 대행자가 정한다
   - 판정 타입이 3개 이상이면 행을 나누고, 진입점을 정할 수 없으면 조사 위임(코드 수정 없이 분해 목록만 회신)을 먼저 보낸다(§4)
   - 새 파일은 `진입점: <새 파일 상대/경로.ext>`, 새 디렉터리는 `진입점: <새 디렉터리 상대/경로/>`로 명시한다. 기존 디렉터리를 진입점으로 지정할 때는 경로 끝에 `/`를 쓴다. 번호 목록은 단계 설명에도 쓰이므로, 별개 구현을 나열할 때만 각 항목을 `1. 구현: ...`처럼 표시한다.
   - 삭제·이관·이름 변경은 `remove-legacy`, UI 구성·이벤트 연결은 `build-ui`를 프롬프트에 지정한다
   - 같은 파일을 순차로 고치는 행들의 진입점은 줄 번호가 아니라 선택자·함수 이름으로 쓰고, 진입점에 넣는 요소(버튼·규칙)는 위임 직전 `rg -n`으로 존재를 확인한다(앞 행이 지운 규칙·없는 버튼을 진입점에 넣어 대행자가 멈춤)
   - "모든 모달·모든 버튼"처럼 전수 변경 행의 진입점은 이름 목록이 아니라 전수 `rg` 패턴(예: `rg -n 'role="dialog"' src`)으로 주고, 그 패턴의 모든 결과를 바꾸라고 쓴다(261107 #752 목록에서 빠진 Grid 상세 편집창 때문에 검증 실패 3회)
   - `명령`·`--tests`에는 이미 있는 테스트 파일만 쓰고 새 단언은 그 파일에 추가하게 한다. 없는 테스트 파일을 지정하면 대행자가 `role-agent` 소스 작성 범위(새 검증 소스 금지)로 멈춘다(261107 #753)
