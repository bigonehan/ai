# Verify Work

Use this skill whenever tests are written, changed, run, investigated, or used to claim behavior. Do not read `AGENTS.md`, `.ai/changes/`, Obsidian notes, or `architecture.md` in full; extract and print only the needed sections, lines, or fields with `rg -n` or `grist task-show <id> --project <dir> --section <section>`. Read the row once before testing as `manage-project` `initial-task` §3 says; when a cause lands in `$J` during testing, repair that cause. The project rules own scope and the authoritative consumer.

## No legacy verification artifacts

Do not create separate verification artifact files. Evidence is command output, the real product consumer, and the Table26 records owned by `role-delegator`·`Complete_task`.

## Requirement-to-consumer testing

For every user-visible requirement, map exactly one path:

`start action → producer → transport/handler → authoritative consumer → final effect`

Use the same scenario and meaningful input at every layer. A helper return, ACK, mock, source string, screenshot, build, or intermediate UI state is not final evidence. Read the persisted consumer state directly. Never pass a task by checking only the edited code/label/control in isolation: execute the full feature flow end-to-end so any broken behavior or failure along the connected path is discovered and repaired (`$I`·`$J` recorded and fixed) before `task-confirm`. When a template, prompt, or document payload source used by an external AI/Bridge workflow changes, never stop verification at the preparation API (e.g. `prepare`, file readback, or character/byte length check); always execute the downstream delivery, editor injection, submission, and response consumer path with the real payload size and content. When an AI response updates a persisted document or note (e.g. project initialization applying ChatGPT's response to an Obsidian `.md` file), verify that `responseText` is non-empty, the consumer application endpoint (`/api/obsidian/note/apply-initialization-response` or equivalent) succeeds, template-only instruction fences (`# 중요` / `# 실행 지시`) are removed, and the actual `.md` file on disk is updated with the analyzed sections and extracted scene items. Keep adjacent workflows out of the path and add negative-scope checks when the request names a narrow workflow.

## Boundary rules

- Use `focused/unit → production-boundary integration → built artifact` when the changed behavior crosses those boundaries. If only the output format of an already working diagnostic logger changes, verify the formatter and its existing logger call with focused unit tests; do not require a browser session or whole-flow replay.
- When adding or changing a TypeScript test included by the project's `tsconfig`, inspect its `types` setting before choosing Node imports and run the project's type-check command as well as the focused test. A passing Vitest run alone does not establish that the test compiles in the project build.
- When the user has stated a cause, take it as the diagnostic input and do not reproduce it again; otherwise reproduce the same failure to find the first failing owner boundary. Who records `$I`·`$J` follows Failure and completion below. Record the actual producer value and type separately from the consumer expectation when a value or type mismatch is under investigation.
- Date·time: whenever the code under test creates, converts, offsets, or compares dates, times, epochs, timezones, `today`, `D-n`, deadlines, or year-less `MM.DD` input (product code, scripts, n8n Code nodes alike), read `references/date.md` in full before writing or running the test and follow its injected-clock cases (KST 00:00–08:59 vs UTC included). A fixed date-string conversion alone never passes.
- Preserve typed values. A single Grist cell has one declared type; reject accidental unions, implicit numeric-string conversion, `String(value)`, tuple-last-element ID guesses, and uncontracted fallback parsers.
- For external APIs, test operation identity, owner, operation, boundary, attempt, result, and thread role while masking credentials, authorization data, raw payloads, and private paths.
- Test effect cardinality and ordering, retry before/after mutation, response loss, timeout, duplicate request IDs, fan-out/fan-in, bubbling, cleanup, reload, restart, and stale-instance removal when those boundaries exist.
- For workflows that can be triggered concurrently per item, slot, or project (e.g. multi-project initialization, batch generation, or multi-tab Bridge delivery), never test only a single isolated request: verify 2+ concurrent independent requests (`Promise.all` or back-to-back triggers across distinct keys/tabs) and confirm that (1) prompt submission is not blocked behind a previous request's or site's long response wait, (2) tab focus, hydration before model selection, and debugger attachment do not collide when tabs move to the background, and (3) timeout budgets obey a strict hierarchy (`clientTimeout >= relayTimeout >= workerResponseTimeout + submissionQueueBudget`) without re-sending large payloads on every status poll.
- For path, file output, search/discovery, or sequence/frame/range behavior, never pass verification by checking only the default start (0 or 1) or only the start/end boundary: choose a randomized non-default range (`start > 1`, distinct `mid`, and `end`, with `start < mid < end`) and verify the start, middle, and end items/frames/lines/files across that random range, reading back targeted lines/fields via `rg -n` (never dumping full files or objects).
- For a reported browser/widget/extension failure, first confirm the running actor (listening pid and start time vs. the newest server source mtime; `dispatch-agent` `runtime-fresh` does this for verifiers) — a stale or orphan runtime is replaced before any log or source is read — then use the user's observation and existing development-mode logs to locate the failing boundary without wasting time reproducing a known cause before editing. However, **after repair, never rely on mocked unit tests (`vi.spyOn(fetch)`), isolated `curl` checks, or persisted DB/log state alone to skip CDP.** Never monkey-patch or stub extension service worker, background, or page runtime functions (e.g. overwriting `openTab`, `applyDocumentPrompt`, or `waitForDocumentTextResponse` via `Runtime.evaluate` / WebSocket in the live worker, or posting synthetic `window.postMessage` events that bypass the widget's real consumer handler) during CDP verification. Whenever the product has a browser/widget/extension runtime (`runtime :`), always verify the deployed runtime in the shared CDP browser from the real start action through the rendered screen state (e.g. `img.complete && img.naturalWidth > 0`, absence of error banners) and authoritative consumer result. An edit limited to an already working logger's output format uses the focused unit boundary above.
- Do not pass a web, widget or extension change by adding unrelated contracts, mock gates or unit tests only. The real deployed runtime (`runtime :`) check in the shared CDP browser, from the start action through the final rendering (e.g. `naturalWidth > 0`) and consumer result, is run once after deployment by the verifier (`dispatch-agent --role verifier`, `role-verifier`); implementers stop at unit and production-boundary tests, and the main session checks only `exit`·`last`. This catches integration and authentication errors before the user sees them.
- A user-requested drag interaction passes only on the verifier's on-screen check in `run-cdp` `references/action.md`; unit tests, synthetic events and DOM reads support diagnosis only.

## Skills for runtime and records

- Browser runtime checks in this document are run by the verifier (`role-verifier` routes `runtime :` web·widget·extension rows to `run-cdp`).
- Drive the user-visible start action and read the page with the `access-stagehand` skill (`openStagehand()`, `act`/`observe`/`extract`).
- Read and write Table26 (`$H`, `$I`, `$J`) and other Grist data with the `access-grist` skill.

## Runtime separation

The default project test command runs unit and production-boundary checks only. An explicit project runtime command is reserved for the final whole-flow check after all Table26 items are submitted (`검증`). If the user has already identified a cause and harmful effect, take them as the diagnostic input and repair the effect's owner boundary first. Do not reopen UI, reread logs, or check installation merely to prove the same cause before editing. For a versioned runtime, after repair compare the installed artifact version with the version of each running actor that actually participates in this request's start action and final effect. Read UI version only when UI changes or UI interaction is part of that flow; do not open a plugin window to validate a service-only import or deletion fix. A mismatch fails the whole-flow check: do not count the consumer result as completion evidence or run `flow-wait` until the running versions match. Do not require this comparison for a runtime without versions. Do not substitute a mock browser, blank page, endpoint health, target discovery, build output, or log existence for the final consumer readback.

## Verification bottleneck diagnosis and source repair

This section applies to checks an implementer or verifier runs itself. A delegator waiting on `dispatch-agent` does not read task logs or set its own timer; it follows the `case=` file on the result line (`manage-project/references/cases/`).

- Whenever a verification or runtime check command is sent to the background, **always set a 5-minute wakeup timer or timeout check in the same turn before waiting**, because a hung background process will never wake the agent on its own.
- When the 5-minute timer fires (or when verification/API exploration takes 5 minutes or more), immediately inspect the task log and intermediate step logs (`[verify-step]` / `[stagehand-step]` / `[stagehand-bottleneck]`) across each boundary (`cdp-attach`, `extension-ready`, `start-action`, `transport`, `consumer-readback`, `session-close`) to identify the exact stage where the bottleneck occurs. Do not mask it by slapping a hard command timeout on it.
- A single API lookup, gate check, or verification path taking minutes means there is a defect or bottleneck in the source code itself (e.g., blocking `stdin`/IPC reads, unclosed keep-alive WebSocket/timer handles after `session.close()`, backgrounded processes holding parent stdio pipes without `</dev/null` and `disown`, repeated full-file scans or regex compilation inside loops, or unbounded polling).
- Immediately inspect the running process and intermediate step logs, pinpoint the exact bottleneck boundary, and fix the source code so the operation completes at normal speed. Report the bottleneck cause and fix as one line in the final message; the delegator records it (`role-delegator`).
- Before running any Stagehand runtime check, check the relevant sections/lines of `~/ai/skills/access-stagehand/references/attach-notes.md` (`먼저 할 일`) and the project's `.ai/docs/performance.md` via `read-architecture` or `rg -n` (never reading full files): use `session.page` / `session.pages` directly (do not call non-existent `page.frames()` or `stagehand.context`), and use `node --experimental-transform-types --input-type=module -e` when importing `.ts` files alongside `openStagehand()`.
- `openStagehand()`'s `session.close()` unrefs remaining keep-alive handles automatically and emits `[stagehand-bottleneck]` every 60s while open; in custom scripts, ensure all timers/sockets are closed or call `process.exit(0)` after `await session.close()` in `finally`.

## Failure and completion

Failure records (`$I`·`$J`, `$H=진단`), repair dispatch and the `확인` transition belong to the delegator (`role-delegator` 하는 일). An implementer ends at `task-submit` (or, in 재현 mode, after writing `$J` with `task-red`); a verifier reports the failing boundary in its last line.
