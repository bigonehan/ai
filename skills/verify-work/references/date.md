# Date·time 테스트 규칙

날짜·시각·기간·타임존·epoch·`D-n`·마감일·"오늘"을 만들거나 바꾸거나 비교하는 코드(n8n Code 노드, 스크립트, 제품 코드 모두)를 테스트할 때 이 파일 전체를 따른다. 고정 날짜 문자열 하나를 변환해 보는 것만으로는 통과가 아니다.

## 1. 먼저 할 일 — 시계 의존 지점 목록

- 대상 코드에서 `rg -n "new Date\(\)|Date\.now|today|getDate|getMonth|getFullYear|getHours|setDate|toISOString|toLocale|currentYear|D-|86400|epoch|timezone|TZ"`로 시계·타임존 의존 지점을 모두 찾는다. 한 지점만 고쳤어도 같은 파일·워크플로의 나머지 지점을 같은 기준으로 판정한다.
- 각 지점에 대해 `기준 타임존(사용자 기준 KST) · 실행 환경 타임존(서버·컨테이너·CI, 보통 UTC) · 저장 형식(Date 셀 epoch 초, YYYY-MM-DD 문자열 등)`을 적는다. 둘이 다르면 경계 테스트 대상이다.

## 2. 필수 사례 — 시계를 주입해 돌린다

`Date.now`/`new Date()`를 고정 시각으로 바꿔(함수 인자 주입, `vi.setSystemTime`, `Date.now = () => t` 등) 실행 환경 타임존(`TZ=UTC`)에서 아래를 모두 돌린다. 기대값은 항상 사용자 기준 타임존의 달력 날짜다.

| 사례 | 실행 시각(KST) | 확인 |
|---|---|---|
| 타임존 날짜 경계 | 00:00, 08:59(UTC 전날) | KST 날짜로 계산되는가 |
| 평상시 | 09:00, 13:00, 23:59 | 위와 같은 KST 날짜인가 |
| 월말·연말 | 1/31·2/28·2/29(윤년)·12/31 23:30 | 월·연 넘김이 맞는가 |
| 연도 생략 입력 | `MM.DD`만 주는 목록을 12월·1월에 실행 | 연도를 실행 시각에서 정하고 고정 연도(`2026`)를 쓰지 않는가 |
| 상대 기간 | `D-0`·`D-1`·`D-n`, `n일 전/후` | 기준일 + n이 KST 날짜인가 |
| 왕복 | 저장(epoch·오프셋 적용) → 다시 읽기(역오프셋) | 원래 날짜로 돌아오는가(예: -2일 저장 ↔ +2일 비교) |

## 3. 저장·표시 경계

- Date 셀·DB에는 저장값(epoch 초 등)을 다시 읽어 사용자 타임존 날짜로 바꿔 대조한다. 쓰기 성공·ACK만으로는 통과가 아니다.
- 오프셋(예: 마감 2일 전)은 원본 마감일 → 저장값 → 화면 날짜 세 값을 함께 출력해 차이가 정확히 오프셋인지 본다.
- 로컬 메서드(`getDate`·`setDate`·`toLocaleDateString`)는 실행 환경 타임존을 따른다. UTC 메서드와 명시 오프셋, 또는 `Intl.DateTimeFormat(..., { timeZone: 'Asia/Seoul' })`만 통과로 본다.

## 4. 실데이터 대조

- 외부 사이트·API에서 날짜를 얻으면 실제 항목 1건 이상의 원본 표기(상세 페이지 `접수기간`, 공식 공고 등)와 최종 저장값을 대조한다. 목록의 상대 표기(`D-n`)만 보고 끝내지 않는다.
- 사용자가 틀린 행을 지적했으면 그 행을 기대값 사례로 넣어 고친 코드로 재현·통과시킨다.
- 기존 여러 행의 날짜를 일괄 보정할 때는 **대상 행마다** 저장값과 독립적인 실제 날짜 원본(상세 페이지의 절대 날짜·공식 공고·원본 실행 기록)을 확보해 `행 ID · 원본 날짜와 출처 · 기대 epoch · 보정 후 저장 epoch`를 대조한다. 보정 전 저장값에 같은 초를 더하거나 뺀 결과, 그 값을 역오프셋한 결과, 목록의 `D-n`만으로 만든 날짜는 기대값이 아니다. 원본이 없거나 원본끼리 충돌하는 행은 성공 건수에서 빼고 미확인 행 ID로 남긴다.
- 수집 경로가 여러 개인 일괄 보정은 경로별 실제 항목을 대조하고, 사용자가 지적한 행은 전부 포함한다. 전체 대상의 독립 원본 대조가 끝나기 전에는 `전수 일치`·`불일치 0건`으로 보고하지 않는다.
